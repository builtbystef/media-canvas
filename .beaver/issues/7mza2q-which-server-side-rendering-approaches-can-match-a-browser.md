## Question

Which server-side rendering approaches can match a browser editor pixel-for-pixel, and at what cost? Survey headless Chromium (Playwright), Skia (CanvasKit, skia-python), SVG pipelines (resvg, librsvg), satori, node-canvas/Konva. Judge each on text/font fidelity, image handling, determinism, throughput at hundreds-to-thousands of renders, operational complexity in FastAPI + workers, and licensing. Gates node 53lwlc (design document format) and node kjz6f0 (rendering pipeline).

## Answer

No renderer surveyed claims pixel parity with a browser. Satori disclaims it in writing; node-canvas publishes a compatibility table of its divergences; Skia/CanvasKit make no parity claim and its Canvas2D layer deliberately disables the one Blink-compatible formula it has. **Pixel parity is therefore not something to select for. It is something to design out: the editor and the worker must run the same engine over the same inputs, and every remaining variable (fonts, hinting, antialiasing, scale factor, color profile, CPU code path) must be pinned.**

Exactly two architectures do this, and both should be prototyped in node kjz6f0:

**Candidate A - one Chromium, both sides.** The editor renders the design document to DOM/SVG in the browser; the worker renders the identical markup in headless Chromium via Playwright and calls captureScreenshot / printToPDF. Same engine, and PDF comes out vector with subsetted embedded fonts for free. Cost: Playwright states outright that rendering varies by host OS, hardware, headless mode and power source, so parity is bought with discipline - one pinned container image, fonts pinned through fontconfig, and one fixed choice between chrome --headless and chrome-headless-shell (since Chrome 132 these are two different renderers in the same image). Heaviest runtime of the set.

**Candidate B - one resvg, both sides.** The design document serializes to SVG; the worker rasterizes with resvg; the editor previews through the very same resvg compiled to WASM (resvg-js ships a WASM backend). This is the only project in the survey that makes an explicit reproducibility claim, and it is the strongest one available: identical pixel values for the same file across x86 Windows and ARM macOS, earned by using no system libraries at all. Cost: PNG only - no PDF backend - and no native text rendering, so the editor cannot use browser text layout for anything that must match. resvg covers the whole MVP feature list otherwise.

The MVP cut in node ylg1wr fits SVG almost exactly: gradients, drop shadow, borders, opacity, clip, groups, placed SVG, images are all resvg-supported SVG 1.1; the cuts already made (no blend modes, no inner shadow, no background blur, no gradients on text) remove the features that break both engines. That is a real point in favour of an SVG-shaped document format for node 53lwlc.

Eliminated: satori (states it does not guarantee matching browser output, no kerning/ligatures/OpenType features, no RTL, flexbox-only layout that does not model an absolutely-positioned design canvas, SVG string output only); node-canvas + Konva/fabric (Cairo+Pango, ships a wiki of known divergences, no ctx.filter, shadow-blur crash note, no parity or determinism claim); librsvg (LGPL-2.1, textPath entirely unsupported, no font-face or font-buffer API, text shaping documented as broken across spans, emoji "inadvertently broken", no determinism claim); CanvasKit as the sole engine (its Canvas2D layer does no shaping, no kerning, no font fallback and has no textAlign/textBaseline/filter - shaping requires the separate Paragraph API - and it is built with skia_enable_pdf=false, so no PDF, and it has no Python binding).

## Findings

### 1. Nobody promises browser parity; the spec does not require it

- The WHATWG canvas chapter specifies fillText/strokeText only down to glyph shapes "positioned on a common coordinate space" - rasterization of those shapes is unspecified. Antialiasing appears only as an optional implementation technique. fontKerning "auto" is explicitly "applied at the discretion of the user agent". https://html.spec.whatwg.org/multipage/canvas.html
- Satori: "Satori does not guarantee that the SVG will 100% match the browser-rendered HTML output since Satori implements its own layout engine based on the SVG 1.1 spec." https://github.com/vercel/satori (README, main)
- CanvasKit source carries Blink's legacy shadow-blur formula commented out, with the note that it is "against the spec", left "in case any clients are interested in using it to match Blink exactly". Default behaviour deliberately does not match Blink. https://github.com/google/skia/blob/main/modules/canvaskit/htmlcanvas/canvas2dcontext.js
- node-canvas publishes its divergences as a Compatibility Status wiki rather than a parity claim. https://github.com/Automattic/node-canvas/wiki/Compatibility-Status
- Skia's only cross-platform statement is API portability, not pixel identity. https://skia.org/

### 2. What actually varies, when the engine is nominally the same

- Chromium collects the per-host text variables in one struct, gfx::FontRenderParams: antialiasing, subpixel_positioning ("fractional X positions for glyphs"), autohinter vs the font's own bytecode, embedded bitmaps, hinting (NONE/SLIGHT/MEDIUM/FULL), subpixel_rendering (NONE/RGB/BGR/VRGB/VBGR), text_contrast, text_gamma - resolved at runtime per host by GetFontRenderParams. https://chromium.googlesource.com/chromium/src/+/main/ui/gfx/font_render_params.h
- Skia's SkFontHinting changes the outlines themselves: kNormal "modifies glyph outlines to improve contrast", kFull "for maximum contrast". SkSurfaceProps carries an LCD pixel geometry plus textContrast/textGamma, and the default constructor is documented as "platform-default contrast/gamma". https://skia.googlesource.com/skia/+/main/include/core/SkFontTypes.h , .../SkSurfaceProps.h
- FreeType: "Selecting a different [hinting] mode usually causes changes in both the outlines and the rasterized bitmaps"; LCD render modes produce bitmaps 3x the width (or height) of the outline; the TrueType interpreter version is selectable at build time and via the FREETYPE_PROPERTIES environment variable, and "If subpixel hinting is on, many TrueType bytecode instructions behave differently". https://gitlab.freedesktop.org/freetype/freetype/-/blob/master/include/freetype/freetype.h , .../ftdriver.h
- Font fallback is decided above the shaper: HarfBuzz's manual states shaping "is the extent of HarfBuzz's responsibility" and that it will not help with strings needing more than one font. Skia's SkFontMgr::matchFamilyStyleCharacter is documented as using "the system fallback". So a missing glyph resolves differently per host unless the font set is pinned. https://harfbuzz.github.io/what-harfbuzz-doesnt-do.html , https://skia.googlesource.com/skia/+/main/include/core/SkFontMgr.h
- Chromium's own projects assume this: web tests check in per-platform baselines with a documented fallback tree; the Linux web-test doc warns that a newer Ubuntu gives "pixel test failures due to changes in freetype or fonts" and that "some pixel tests may fail due to processor-specific rounding errors"; Skia Gold exists because "it is not uncommon for tests to produce images that are visually indistinguishable, but differ in a handful of pixels". https://chromium.googlesource.com/chromium/src/+/main/docs/testing/web_test_baseline_fallback.md , .../web_tests_linux.md , https://github.com/chromium/chromium/blob/main/docs/gpu/gpu_pixel_testing_with_gold.md
- Chromium's own web-test harness pins fonts rather than flags for text determinism: its Linux platform init does nothing but test_fonts::SetUpFontconfig(). https://chromium.googlesource.com/chromium/src/+/main/content/web_test/browser/web_test_browser_main_platform_support_linux.cc

### 3. Candidate A - headless Chromium via Playwright

- Playwright's own warning: "Browser rendering can vary based on the host OS, version, settings, hardware, power source (battery vs. power adapter), headless mode, and other factors... For consistent screenshots, run tests in the same environment where the baseline screenshots were generated." https://playwright.dev/docs/test-snapshots
- Resolution comes from the browser context's deviceScaleFactor (default 1), NOT from screenshot scale, which is only "css" | "device". Puppeteer instead puts a numeric scale inside clip. https://github.com/microsoft/playwright/blob/main/docs/src/api/params.md , https://pptr.dev/api/puppeteer.screenshotclip
- Screenshot options include clip, omitBackground (png/webp only), animations: "disabled", caret: "hide" (default). https://playwright.dev/docs/api/class-page#page-screenshot
- PDF is real vector: Skia's PDF backend emits text operators and embeds all fonts, TrueType subsetted via HarfBuzz. But SkPDF "expands" what it cannot represent - image filters, path effects, colour filters and non-gradient shaders force rasterization, and "text-as-text is lost". So CSS filter/blend/mask regions silently degrade in PDF. https://skia.org/docs/dev/design/pdftheory/ , https://skia.org/docs/user/sample/pdf/
- page.pdf() uses print media by default and modifies colours for printing unless -webkit-print-color-adjust is forced; options include printBackground (default false), width/height/margin, preferCSSPageSize. Puppeteer alone has omitBackground for PDF. https://github.com/microsoft/playwright/blob/main/docs/src/api/class-page.md , https://pptr.dev/api/puppeteer.pdfoptions
- Font readiness: Puppeteer waits for document.fonts.ready before PDF by default (waitForFonts, default true); Playwright has no such option and it must be awaited manually. The CSS Font Loading spec warns "the user agent may need to iterate over multiple font loads before the ready promise is fulfilled", so one await is not always enough with fallback chains. https://pptr.dev/api/puppeteer.pdfoptions , https://www.w3.org/TR/css-font-loading-3/
- Determinism levers with primary backing: --disable-lcd-text ("Disables LCD text"), --disable-font-subpixel-positioning ("affects the character glyph sharpness, kerning, hinting and layout"), --disable-skia-runtime-opts ("Do not use runtime-detected high-end CPU optimizations in Skia... forcing a baseline code path"), --force-device-scale-factor, --force-raster-color-profile, --disable-gpu, and the experimental meta-flag --deterministic-mode (requires driving BeginFrames over CDP). https://chromium.googlesource.com/chromium/src/+/main/content/public/common/content_switches.cc , .../ui/gfx/switches.cc , .../ui/display/display_switches.cc , .../headless/public/switches.h
- Headless is now two renderers: since Chrome 132.0.6793.0 the old headless is a separate binary, chrome-headless-shell, and Playwright's Docker image installs both. Which one you launch is a fidelity decision. https://developer.chrome.com/docs/chromium/headless , https://github.com/microsoft/playwright/blob/main/utils/docker/Dockerfile.noble
- Fonts on Linux resolve through fontconfig; libfontconfig1 is a required dep and Playwright's image installs a specific font set (Liberation, Noto Color Emoji, Unifont, IPAfont, WQY Zenhei, ...). A bare container renders tofu. https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/registry/nativeDeps.ts
- Ops: official image mcr.microsoft.com/playwright(/python), pin the version tag; --ipc=host is required or "Chromium can run out of memory and crash"; --init recommended; no Alpine/musl. BrowserContexts are "fast and cheap to create" and fully isolated within one browser - that is the per-job unit. https://playwright.dev/docs/docker , https://playwright.dev/python/docs/browser-contexts
- Python: "If your modern project uses asyncio, you should use async API." And "Playwright's API is not thread-safe... create a playwright instance per thread." FastAPI runs plain def path operations in a threadpool. https://playwright.dev/python/docs/library , https://fastapi.tiangolo.com/async/
- Licensing: Playwright Apache-2.0, Puppeteer Apache-2.0, Chromium source BSD-3-Clause (bundled third-party components carry their own).

### 4. Candidate B - resvg both sides

- The reproducibility claim, and its mechanism: "Since resvg doesn't rely on any system libraries it allows us to have reproducible results on all supported platforms. Meaning if you render an SVG file on x86 Windows and then render it on ARM macOS - the produced image will be identical. Each pixel would have the same value." The stated cost of that same property: "No native text rendering". https://github.com/linebender/resvg (README, main)
- resvg's own regression suite pins fonts explicitly: --skip-system-fonts --use-fonts-dir tests/fonts --font-family "Noto Sans" ... System fonts are the escape hatch that voids the guarantee. https://github.com/linebender/resvg/blob/main/crates/resvg/tests/README.md
- Feature coverage matches the MVP cut: LinearGradient, RadialGradient, Pattern, ClipPath, Mask, Image are public tree nodes; filter primitives include DropShadow and GaussianBlur, and usvg states "All filters are supported. Including filter functions". Embedded images: JPEG, PNG, GIF, WEBP, base64 or external. Unsupported list is animation/scripting/font elements/direction/kerning attributes - none of them in the MVP. Around 1600 SVG-to-PNG regression tests, with a public support table. https://github.com/linebender/resvg/blob/main/docs/unsupported.md , .../crates/usvg/src/tree/mod.rs , .../filter.rs , .../crates/usvg/README.md
- Text: shaped in-process, text-on-path supported (TextPath / TextFlow::Path), fonts supplied through fontdb with a programmatic FontResolver hook. Text is converted to paths by usvg, documented as lossless except for SVG-table glyphs outside pure SVG 1.1/2.0 and some COLR features (conical gradients, some gradient transforms, some blend modes). As of 0.48.0 (2026-07-31) the stack is skrifa + harfrust, not ttf-parser + rustybuzz - the README link list is stale on this point. https://github.com/linebender/resvg/blob/main/crates/usvg/src/tree/text.rs , .../CHANGELOG.md
- Output is PNG only. The CLI is resvg [OPTIONS] in-svg out-png; there is no PDF or PS backend. This is the decisive limitation against the MVP's digital RGB PDF export. https://github.com/linebender/resvg/blob/main/crates/resvg/src/main.rs
- Bindings: resvg-js (npm @resvg/resvg-js 2.6.2, MPL-2.0) has Node and pure-WASM backends, PNG output plus a usvg-simplified SVG string, and font controls fontFiles / fontDirs / loadSystemFonts (default true, "if set to false, it will be faster") / fontBuffers in WASM. Its own README benchmark: 12 ops/s vs sharp 9, skr-canvas 7, svg2img 6 (no hardware stated). https://github.com/thx/resvg-js
- Python: there is no first-party binding - the resvg repo has only c-api, resvg, usvg crates. The de-facto binding is third-party resvg_py (PyPI 0.3.4, MIT), whose whole API is one function svg_to_bytes(...) -> bytes. Which resvg version a release pins is exposed only at runtime. A FastAPI worker would either use that, the C API, or shell out. https://github.com/linebender/resvg , https://github.com/baseplate-admin/resvg-py
- Cost notes: no throughput figures published; the CLI skips fontdb init when there is no text because "fontdb initialization is pretty expensive"; the binary is under 5MB with no external deps. License Apache-2.0 OR MIT.

### 5. The rejected engines, with the sentence that rejects each

- satori (MPL-2.0): parity disclaimer above, plus "Advanced typography features such as kerning, ligatures and other OpenType features are not currently supported. RTL languages are not supported either." display is flex/contents/none only; no z-index ("Elements that come later in the document will be painted on top"); no calc; fonts must be supplied as buffers, WOFF2 unsupported; output is an SVG string requiring a separate rasterizer. https://github.com/vercel/satori
- node-canvas 3.2.3 (MIT) + Konva (MIT) / fabric (MIT): Cairo + Pango, so it does get HarfBuzz shaping transitively, and it does emit PNG/JPEG/PDF/SVG. But ctx.filter is "No support", direction is "No support", measureText omits bounding-box metrics, and "A1, A8, RGB30 and RGB16_565 with shadow blurs may crash or not render properly". Konva's own framing is telling: install canvas "for rendering backend... Then you can use the same Konva API" - same API, different rasterizer, which is exactly the parity trap. https://github.com/Automattic/node-canvas , https://github.com/konvajs/konva
- librsvg (LGPL-2.1): "textPath is not supported at all"; font-face and WOFF unsupported; text shaping "is not done" across spans; "Emoji got inadvertently broken". It does uniquely offer PDF/PS/EPS output from rsvg-convert. No determinism claim. https://gitlab.gnome.org/GNOME/librsvg/-/blob/main/devel-docs/text_layout.rst , .../rsvg-convert.rst
- CanvasKit 0.41.1 (BSD-3-Clause): the Canvas2D emulation "does not perform typeface fallback for characters not found in the Typeface. It does not perform kerning or other complex shaping; glyphs are positioned based on their default advances", and lacks filter, textAlign, textBaseline, direction, letterSpacing, createConicGradient. Real shaping needs the separate Paragraph API (HarfBuzz + ICU). Built with skia_enable_pdf=false, so PNG/JPEG/WEBP only. Node use is documented and supported, but no browser-parity or determinism claim is made anywhere.
- Adjacent Skia options worth remembering for the PDF gap: skia-python 144.0 (BSD-3-Clause, pybind11, wheels for CPython 3.8-3.14, requires OpenGL/libEGL/fontconfig on Linux) binds both the PDF document API and skparagraph; @napi-rs/canvas 1.0.3 (MIT, Skia chrome/m151, zero system deps) has the fullest Canvas2D surface of the set - filter, createConicGradient, letterSpacing - plus HarfBuzz/ICU shaping, GlobalFonts registration, and skia_enable_pdf=true with PDFDocument and link annotations. Neither claims browser parity.

### 6. Throughput, honestly

No project in the survey publishes throughput or memory figures for its own renderer. Playwright's documented guidance runs the other way - for CI it recommends one worker and sharding over raising parallelism, and defaults to half the logical cores. The only per-job cost guidance with primary backing is that BrowserContexts are cheap and browsers are not. Any hundreds-to-thousands-per-hour number for this project has to come from measurement in node kjz6f0, not from documentation.

## Unresolved

- **Contradiction on Chromium's --font-render-hinting.** One search found it in headless/public/switches.h ("Sets font render hinting when running headless, affects Skia rendering and whether glyph subpixel positioning is enabled. Possible values: none|slight|medium|full|max. Default: full."). A second search of content_switches.cc, ui/gfx/switches.cc, headless_content_main_delegate.cc and headless_command_switches.cc on main did not find it, and headless/app/headless_shell_switches.cc no longer exists. Both sides recorded; treat the flag as probably present but verify against the exact Chromium build the prototype pins.
- Which flags --deterministic-mode actually sets - the implementation site was not located. It is documented as experimental and requires BeginFrames over CDP.
- No primary source quantifies pixel differences between GPU rasterization and SwiftShader, nor asserts SwiftShader is bit-identical across machines.
- No primary source gives MB-per-page, MB-per-context, or browser cold-start figures.
- Whether a HTML5 canvas element inside a page is rasterized in Chromium's PDF output was not confirmed from a primary source (it follows from SkPDF's expansion rules, but no doc states it).
- Chrome for Testing's licensing terms (shipped in Puppeteer's image) were not verified.
- Which resvg version any given resvg_py release pins is not documented outside runtime.
