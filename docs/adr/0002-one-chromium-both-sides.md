# 0002 — One Chromium renders both editor and export

**Context.** Exported output must match what the editor showed. The research (node `7mza2q`) established that no engine matches a browser pixel-for-pixel, so parity means running the same engine on both sides. Two candidates survived to a prototype (node `gqr8bf`): headless Chromium via Playwright, and resvg native + WASM. The prototype measured both against a hard-case document in the ADR-0001 format; evidence lives on branch `prototype/render-fidelity`.

**Decision.** The editor renders the document's compiled markup in the browser; the render worker screenshots the identical markup in headless Chromium driven by Playwright, and produces the digital RGB PDF via `printToPDF` (vector, real text). The worker runs in a pinned environment: one container image, one pinned Chromium build, one pinned headless flavor, fontconfig-pinned fonts.

**Reason.** resvg's byte-identical parity claim held exactly in the prototype (native vs WASM: zero differing pixels), but Chromium won on the whole: vector PDF comes free from the same engine, the editor DOM is (nearly) the render markup so no second canvas implementation exists to drift, and measured throughput (~166 ms/render at 8 concurrent pages; ≈2.8 min per 1,000 assets on one host) suffices. The accepted cost is that parity is visual, not byte-exact — Chromium differs from itself by 0.53% of pixels (glyph antialiasing only) across headless flavors — so render regression testing uses a perceptual tolerance (node `ud46e4`), and the pinned worker image is a hard deployment requirement.
